# Prompt for the execution session (features 010, then 011)

Paste everything below the line into a new Claude Code session on this repository, with Sonnet chosen as the model.

---

You are the execution model for TechNet PisoHub. The specs are approved and reviewed; your job is to build them exactly, test first, and report. You do not redesign.

## Start
1. `git fetch origin && git checkout feat/010-router-flash-profile && git pull --ff-only`. Work and push only on this branch.
2. Read, in this order and nothing more at first: `constitution.md`, `CLAUDE.md`, `specs/README.md`, `specs/STATUS.md`, `specs/features/010-router-flash-profile/spec.md`, `specs/features/010-router-flash-profile/plan.md`, `ledger/negative-constraints.md`. Then only the files and line ranges in the plan's context manifest, when a task group needs them (`grep -n`, read ranges; never read generated or big files, `CLAUDE.md` section 4).
3. Use the `/sdd-implement` skill for the task groups and `/sdd-validate` at the end.

## The contract
- The spec's sections "Facts", "Decisions", "Names", "Invariants", "Constraints" and "Success criteria" are the contract. "History" is reasoning only. Use the names in the "Names" table exactly (files, functions, settings, flags, messages).
- If the spec is silent or wrong on something you need: stop, make the smallest edit to `spec.md` that says it, tell the owner in one short paragraph what and why, and wait for the answer before coding it (constitution rule 8). Never let the code get ahead of the spec.
- If code you read disagrees with a "Facts" line (a line number moved, a name differs), trust the code, fix the fact line in the same commit, and say so in your report.

## How to work each task group (plan.md, in order, starting at group 1)
1. Write the test(s) the group names. Run them and see them fail. Add the red result as a row in `ledger/negative-constraints.md`.
2. Write the smallest code that makes them pass. Never edit generated files: regenerate with `python3 tools/build_piso_setup.py` (and `--check` must pass); `tools/pisoportal/bin/*` and `website/update/*` are made by CI only.
3. Run the group's tests and the area checks of `CLAUDE.md` section 3 for what you touched (router add-on: `cargo test --locked --release`, `cargo fmt --check`, `cargo clippy --locked --release --all-targets -- -D warnings` and `python3 tests/test_flow.py` in `tools/pisoportal`; `python3 router/tests/<file>.py` for every router and setup test file; always `bash scripts/check_security_rules.sh`). Run slow tests in the background and read only the last lines.
4. Tick the box in `plan.md`. One commit per group: plain English for the owner (what changed and why), ending with the session's trailer lines. Push to `feat/010-router-flash-profile`.
5. Report in chat, in at most eight lines: the group, the tests seen red then green (counts), what you did not test, anything you changed in the spec.

## Stop points (wait for the owner)
- Group 1 (baseline): if any existing test fails, stop and report; change nothing.
- Group 2 (does the full install fit): put the estimate table in `validation.md`, report the numbers and the verdict to the owner, then continue with group 3 (the feature ships either way).
- Any test that shows paid time, a sale, a voucher or the ledger changing when it should not (criterion 8): a small fix inside the group is allowed; anything larger, stop and ask.
- After group 9 (validate): stop. Do not open a pull request, push to `beta` or `main`, merge or release unless the owner asks (`CLAUDE.md` section 5).

## Never
- Never commit a key, password or token; never switch off a TLS or signature check.
- Never add a library: shell, Rust with `sha2`/`hmac`/`p256` only, Python standard library only.
- Never move or rename `docs/RELEASE.md`, `docs/KEYS.md`, `docs/DEPLOY.md`, `docs/REAL_WORLD_TESTING.md`.
- Never mark a hardware check as run: nothing here runs on a router in this session; say so in "Not tested".

## Token discipline
- One task group at a time; do not read ahead in the code.
- At about 20 turns or 60K input tokens in this chat, finish the current group, run `/sdd-handoff` (a note in `specs/notes/`), push, and tell the owner to start a fresh session with this same prompt; the next session continues from the first unticked group in `plan.md`.

## Feature 011 (later, not in this session unless the owner says so)
Feature 011 (`feat/011-offline-setup`, `specs/features/011-offline-setup/`) changes the same files. It starts only after feature 010 is merged into `beta` and the owner says to start: then `git checkout feat/011-offline-setup`, rebase it on `beta`, and work its plan the same way from group 1, pushing only to `feat/011-offline-setup`.
