# Feature 024: each device's type on its lock and home screens

Status: **draft**   Branch: `feat/024-device-type-labels`   Area: firmware + app (one message contract, changed on both sides together)
Backlog rows: owner request 2026-10-24 (builds on feature 013 branding and the phone profiles)   Release: firmware and app

## Intent
A rental tablet should say **PisoTab**, a basic phone **PisoPhone**, a gaming phone **PisoPhone Pro**, on its own lock screen and
home screen, so customers and the owner see at a glance what they are renting. The owner picks the type for each phone slot on the
box's admin page from presets, or types a custom name (for example "PisoTab Kids"). Serves the shop owner's labelling; no money or
time changes.

## What is there today (read from the code)
- **Phone profiles** already exist on the box (`esp32_firmware/include/PhoneProfiles.h`, settings page in
  `esp32_firmware/web/portal-modals-phones.js` from line 237): up to 8 named profiles, each with its own *minutes per peso*, and a
  profile chosen for each phone slot. Names are 1 to 20 characters. Profile 0 is the box's standard rate and has no name.
- **The phone is never told its profile.** The app has no use of a profile (grep finds none). Only the *rate* reaches it.
- The lock and home screen header shows one **box-wide** title (feature 013, `ShopBranding.kt`, default "PisoPhone", at most 20
  characters). Every phone gets the same branding push (`ShopBranding.h`: palette, shop name, title, density).
- So today a tablet and a phone both say whatever the one box-wide title says.

## Invariants touched
- Money and time: **not touched on purpose.** A profile also carries the *rate* that credits minutes for pesos. This feature adds a
  *label* and presets only; it must never change a rate. Presets create a profile with the **standard rate** unless the owner sets
  another. A test proves: changing or sending a label changes no minutes per peso and no credit.
- Only owner-signed software: not touched. The new field rides the existing signed push.

## Constraints
- The box <-> phone message contract changes on **both sides in one change** (`protocol/gen_vectors.py`,
  `esp32_firmware/host_tests/protocol_contract_test.cpp`, the app's parser and its tests).
- **Old and new work together:** an old app with a new box ignores the new field; a new app with an old box shows the title as
  today. No phone is ever left without a header text.
- The label is owner-typed: the same cleaning on both sides as the other branding text (control characters, `| ; " \ < > &` refused,
  at most 20 bytes), never a file name, URL or command.
- The branding push has a size limit (`ShopBranding.h` line 129 to 142); the label must fit or the push is refused loudly, as in 013.
- Generated files are regenerated by their scripts (`scripts/embed_web.py`), never edited by hand.

## Success criteria
1. **Presets and custom names on the box.** The phone profiles settings offer three presets, **PisoPhone**, **PisoTab**,
   **PisoPhone Pro**, one tap each, and still accept any custom name; the admin page shows which label each slot has.
2. **The slot's label reaches the phone.** The phone gets the label of its own slot in its branding push; a host test checks the
   message bytes against `protocol/gen_vectors.py` (red first: today no label exists).
3. **The screens show it.** The lock screen and the home screen header show the slot's label as the title. A slot with no profile
   (the standard one) shows the default label (Owner decision 1). A phone that never got a label (old box) shows today's title.
4. **No rate changes.** A host test: for every profile, rate lookup before and after setting, renaming or sending a label is identical.
5. **Old and new together** (tested): new app with old box shows the box-wide title; old app with new box is unaffected (the
   parser tests ignore the extra field).
6. A name that does not fit the push, or is refused by the cleaning, is refused on the box page with a message; nothing is saved.
7. Host tests (sanitizers), clang-format 23.1.2, protocol vectors, ktlint and detekt with the CI jars, CI's unit tests and
   goldens pass. **Hardware check RS49** (one tablet and one phone on one box; rename a label; unplug the box and restart a phone)
   is added to `docs/REAL_WORLD_TESTING.md` and stays unticked until run.

## Out of scope
Different rates per preset (the presets use the standard rate; the owner can still set a rate per profile as today), per-phone
shop names, the marquee (feature 023), icons or pictures per device type, renaming by the phone itself.

## Owner decisions (please answer; defaults in bold)
1. **Which wins in the header, the slot's label or the box-wide header title?** My proposal: **the slot's label wins; the box-wide
   title stays as the fallback for a phone with no label.** The standard profile (no name) shows the default label **"PisoPhone"**.
2. Should the label also appear in the pairing list on the box page and on the phone's setup screens? **Only on the lock and home
   screens plus the box's slot list.**
3. Presets: exactly those three, **or** more (for example "PisoTab Lite")? **Three.**
4. May an owner delete a preset profile once created (as any profile today)? **Yes, as today.**
