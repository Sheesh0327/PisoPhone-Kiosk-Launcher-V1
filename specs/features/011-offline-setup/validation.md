> **Part A was removed in router 1.5.26 by feature 041** (the owner chose one install path: the router needs internet for the first setup). The work below passed and is kept as the record; only part B is still in the product.

**Result: all 15 criteria pass. How the tests were run: from the repository root, `python3 router/tests/<file>.py`. One note on the container: in this cloud container `/dev/null` is a regular file (48 stray bytes), not a device, which made the check "the answers went over the connection's input" in `test_pisophone_setup.py` fail on about half of the runs (a child that reads `/dev/null` got that text). The final runs below were made with a proper `/dev/null` device bind-mounted inside a private mount namespace (`unshare -m`), which leaves the container's file alone. On a normal machine and in CI nothing needs doing. Details in the ledger.

## Not tested

- **BusyBox `ash`** (the router's shell): `busybox` is not installed here, so the second pass of `test_install.py` and the "BusyBox-only decoding" case in `test_setup.py` were skipped. The new shell code (`21-local-packages.sh`, the `while read` loop with `set --`, `awk` with `sub`) has therefore **not** been seen under ash. ShellCheck is clean for POSIX sh.
- **Real OpenWrt package lists**: only two fixture sets shaped like 23.05 and 24.10 (alternatives, `Provides`, kernel dependencies, multi-line descriptions). Real `Packages` files, real `opkg list-installed` output and real dependency chains were never read. Version constraints other than the kernel's are not compared.
- **Community package sources** (the owner's Qihoo 360 T6GS): not reached; whether they serve signed indexes is RS36 (c).
- **Real signatures**: `usign` is a stub that checks a hash. The real `usign -V` against OpenWrt's keys was not run. The computer cannot check signatures itself; the router does.
- **https downloads of the sources**: the local server speaks http; https goes through the same `urllib` code but was not exercised.
- **A real ssh** (the fake ssh runs the remote command with `sh` locally); the real password helper path with a factory router that has no password; the web page's progress display during the offline steps (the lines go through the existing activity feed; no browser test of them); Windows and macOS.
- **apk routers** (OpenWrt 25.x): refused by design ("not possible", fallback), never seen.
- **Rust**: `cargo test` and `tools/pisoportal/tests/test_flow.py` were not run (owner, 2026-10-23: no Rust is touched).
- A coin put in **during** the box network switch (RS37 (a)): the claim that it is credited once rests on the existing firmware queue; it was not exercised.

## Money and time
**Part A does not touch payments**: no change to the portal program, the payment queue, the ledger, credit, expiry or deduction; it only changes how OpenWrt packages reach the router during the first setup. **Part B** changes no payment code either: the router tells the box a new Wi-Fi name and password with the existing admin request (`/save`), then switches its own network. During the switch (up to 240 s) the box is off its network; the box records every coin in its own flash queue before anything else and the router credits each payment once afterwards (by coin window id), as before (`docs/ARCHITECTURE.md`; `CLAUDE.md` rule 1). **How this was checked:** by reading the diff (`git diff b1db87f --stat` lists only setup, router test, docs and website files; `esp32_firmware`, `tools/pisoportal` and `app` are not in it); by tests that the command changes no settings but the box network's name, key and flags (`wireless.kiosk_*`, `KIOSK_*` untouched, MAC lock untouched) and stops before changing anything when the box does not answer or refuses; and by the command saying, and asking, before it starts. What was **not** checked: a real coin during a real switch (RS37 (a)).
