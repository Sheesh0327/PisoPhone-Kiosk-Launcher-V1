## Intent
**Part A.** Today the router must have internet during its first setup. A shop owner who sets up the router with the setup program on a computer (before the ISP has connected the modem, or with a flaky line) is stopped. With this feature the computer, which has internet, downloads the installer and the OpenWrt packages the router needs, copies them to the router's RAM, the router checks them, and the setup runs without the router going online. If anything cannot be prepared, the setup says so and uses today's path.

**Part B.** The owner sets up router 2 and coin box 2 while router 1 already runs nearby. Box 2 sometimes joins router 1 instead of router 2 and the pairing fails or is unreliable. The cause is Wi-Fi, not the modem or the internet: during pairing a new box only knows the name built into its firmware, and an older router 1 still broadcasts that same name. This part gives every router's coin box network a name of its own (also on routers set up before per-router names existed), and makes the pairing say what to do when another router is in the way. Nothing here may cost a customer money or time.

## Facts, part A: where the first setup goes online (checked 2026-10-22; line hints refreshed against `beta` `b1db87f` on 2026-10-23)
A1. **Where the first setup goes online today:**
   - the setup program tells the router to `wget` `install.sh` from the website (`installer_command`, `setup/pisophone_setup.py`, line 1874); `install.sh` downloads the installer for the router's CPU and its `.sha256` (the CPU file choice around line 135-144, the download and sha256 check around 149-167, through `fetch()` at line 49);
   - on a factory router this happens twice: once at the factory address, which moves the router to 10.0.0.1 (a network restart, `/tmp` survives), then again at 10.0.0.1 with the answers (`install()`, `pisophone_setup.py`, line 1981; `setup_command`, line 1884, calls `installer_command` again);
   - the installer stops when the router cannot ping 1.1.1.1 or 8.8.8.8 (`preflight`, `setup/src/20-preflight.sh`, line 38);
   - it runs `opkg update`, then installs `opennds curl ca-bundle jsonfilter` when missing and `libmicrohttpd-no-ssl` when no `libmicrohttpd` is installed (`install_packages`, `20-preflight.sh`, lines 43-56, called from `98-setup-flow.sh` line 135, inside `stage1`).
   Nothing else in the first setup needs the router's internet: the coin box pairing, Wi-Fi, portal, isolation and checks are local. `kmod-nft-bridge` is not installed by the setup (it only warns, `75-checks-stage2.sh:15`).
   **Where `install_packages` sits in the flow (checked 2026-10-23, after 010):** `stage1` runs `check_product`, then `preflight` (line 116), then the questions and `review_choices`, and only then `install_packages` (line 135), `extract_payload` and `apply_batch` (line 139), which is the first step that changes the router. Everything between `preflight` and `install_packages` is local question-and-review work — 010 added `check_product`, `confirm_product` and `apply_product` there — so skipping the ping and `opkg update` leaves no other point in `stage1` that needs the router's internet.
A2. **The setup program already talks to the router over SSH** and can send data on a command's standard input: `run_remote(ssh, host, remote, emit, data=None)` (`pisophone_setup.py`, line 1931) calls `ssh.popen(host, remote, "-T", stdin=subprocess.PIPE, ...)` when `data` is given and writes the bytes to `proc.stdin`. The SSH class is named **`Ssh`** (line 1747) — there is no `SshRunner`, and no `subprocess.run(input=...)` call; use `run_remote(..., data=...)`. It uses only the Python standard library (`CLAUDE.md` section 6).
A3. **OpenWrt package sources:** each router lists its own in `/etc/opkg/distfeeds.conf` (`src/gz <name> <url>`); each source has `Packages.gz`, `Packages` and `Packages.sig` (a usign signature over the uncompressed `Packages`). `Packages` gives per package: `Package`, `Version`, `Depends` (comma separated; `a | b` alternatives; version constraints in brackets), `Provides`, `Filename`, `Size`, `SHA256sum`. Community builds (such as the owner's 360 T6GS) list their own sources there.
A4. **Signature checks:** `opkg update` checks `Packages.sig` with `usign` and the keys in `/etc/opkg/keys/` when `/etc/opkg.conf` has `option check_signature`; `opkg install <file>.ipk` from a local file checks nothing. Python's standard library cannot check usign (ed25519) signatures; the router can (`usign -V -m <Packages> -P /etc/opkg/keys -x <Packages.sig>`).
A5. **OpenWrt 25.x replaces opkg with apk** (other index format and signatures). Releases 22.03 to 24.10 use opkg.
A6. **RAM:** `opkg update` keeps all package lists in RAM (`/tmp/opkg-lists`), several MB. The router's update already uses the rule "work in RAM unless `MemAvailable` is under 24000 KB" (`mem_available_kb`, `96-space-backup.sh`, line 15, used at line 23). Feature 010 gave `install.sh` the same rule in `pick_dir` (line 37-42): `DIR=/tmp` with `IN_RAM=1` at 24000 KB and above, `DIR=/root` below. Because offline mode needs at least 24000 KB (decision A6), `$DIR` is always `/tmp` on the offline path, so the installer copy stays in RAM and 010's `drop_installer_copy` (which clears only `$PISO_ROOT/tmp/piso-setup.sh` and `$PISO_ROOT/root/piso-setup.sh`) still covers it.

## Facts, part B: the coin box network's name (checked 2026-10-23, router 1.5.17; line hints verified against `beta` `b1db87f`)
B1. **The name a new box knows:** the firmware has `PisoCoinBox` with the password `PisoCoinBox@Setup` built in (`DEFAULT_WIFI_SSID` and `DEFAULT_WIFI_PASSWORD`, `esp32_firmware/include/SetupGate.h`, lines 19-20); a factory-reset box goes back to them (`esp32_firmware/src/Config.cpp`, lines 759-760, which assign those two constants). The box connects with `WiFi.begin(ssid, pass)` (`esp32_firmware/src/main.cpp`, line 107), which joins the first access point that answers to the name, not the strongest.
B2. **Pairing:** `pair_box` (`setup/src/50-coin-box.sh`, line 32) opens the box network as `PisoCoinBox` with the built-in password and no MAC lock, waits up to `PAIR_WAIT` for a station, then locks the network to that MAC (`lock_box_network`, line 95). Its tips at 60, 150 and 300 s talk about power, firmware and distance; none mentions another router.
B3. **Each router's own names:** since router 1.5.0, a newly set-up router gets `PisoKiosk-<id>` and `PisoCoinBox-<id>`, `<id>` being the last two bytes of its MAC (`router_id`, `setup/src/10-settings.sh`, line 56; `resolve_wifi_names`, line 68; `box_net_ssid`, line 81). After pairing, `rotate_box_wifi` (`50-coin-box.sh`, line 180) gives the box its own password **and the router's own name** in one request (`/save` with `wifi_pass` and `wifi_ssid`), switches the router's network to them, and waits up to 240 s for the box to answer.
B4. **The box stores both in one `/save`, and checks neither** (`esp32_firmware/src/WebServerConfig.cpp`): `wifi_ssid` is stored at lines 233-235 and `wifi_pass` at 237-239, each simply `hasArg` then `putString`, with **no validation** — unlike the rental-phone fields just below (lines 242-257), which are refused when `kioskWifiSsidValid` or `kioskWifiPasswordValid` says no. The box's own two fields also sit outside `#if PISO_HAS_PHONES`, so they work on a PisoWiFi-only box. Consequence for this feature: nothing on the box will reject a bad name, so `own_box_wifi_name` must send a name it has checked itself (constraint below). This is why no firmware change is needed.
B5. **Older routers keep the shared names:** a router set up before 1.5.0 (it has a stored `KIOSK_PASS`) keeps `PisoKiosk` and `PisoCoinBox` (`resolve_wifi_names`, line 71), on purpose, so its phones and box keep working. Its box network is therefore always called `PisoCoinBox`, even after its password was changed. A newer router whose password change failed also stays on `PisoCoinBox` (`rotate_box_wifi` logs "it keeps the built-in one for now (still locked to its MAC)").
B6. **The clash:** while router 2 pairs, a router 1 that broadcasts `PisoCoinBox` answers box 2 too. If router 1 answers first, its MAC lock (or its own password) refuses box 2, the box retries, and may hit router 1 again: pairing is slow or fails. Once router 2 has rotated, box 2 uses `PisoCoinBox-<id2>` and the clash is over; a router 1 on its own name never clashes.
B7. **`piso-setup rotate-box-wifi`** exists (`98-setup-flow.sh`, line 194; listed among the commands at line 151): it sets `BOX_WIFI_ROTATED 0` and runs `rotate_box_wifi`. When the box refuses the request, `rotate_box_wifi` returns without changing the router, but `BOX_WIFI_ROTATED` stays 0, so `box_wifi_key` (`50-coin-box.sh`, line 22) then names the built-in password although the router and box still use their own one (a latent fault; criterion 3 covers it).
B8. **Where the owner sees the router's state:** `piso-setup status` (`cmd_status`, `80-commands.sh`, line 4), the setup summary (`60-summary.sh`), and the setup program's read-only Check-up (`checkup`, `setup/pisophone_setup.py`, line 3972).
B9. **Payments while the box is off its network:** the box records every coin in its own flash queue before anything else and the phone or router credits each payment once when the link is back (`docs/ARCHITECTURE.md`); during a network switch, Wi-Fi customers cannot pay by coin for up to the 240 s wait.
B10. The computer side: every router's LAN is 10.0.0.1 and a factory router is 192.168.1.1, which many modems also use. A computer connected to router 1 or to the modem's Wi-Fi while cabled to router 2 can reach the wrong device (not changed by this feature; see "Questions for later").

## Decisions, part A (approved by the owner, 2026-10-22)
A1. **Only the setup program path.** The one-line installer typed on the router by hand keeps needing the router's internet (there is no computer).
A2. **Offline first, today's path as the fallback.** The setup program prepares the files on the computer before it touches the router. If preparing fails (no source reachable, a package missing, apk router, too little RAM, no usign or no keys), it says why and, if the router has internet, runs today's path; if not, it stops before changing anything.
A3. **The router checks what it installs:** each source's `Packages` against its `Packages.sig` with the router's own `usign` and keys, then each package's sha256 against that `Packages`; the installer against its published `.sha256` as today. Anything that fails: nothing is installed, the setup stops with the reason.
A4. **The router's own sources** (`/etc/opkg/distfeeds.conf`) decide where the computer downloads from, so the packages match the router's release, CPU and kernel.
A5. **Only what is missing** is downloaded: the packages of fact A1 and their dependencies, minus what `opkg list-installed` shows.
A6. **RAM only:** everything goes to `/tmp/piso-offline/` (about 1.6 MB installer, the packages, and the `Packages` files of the sources used). The setup program deletes it over SSH after the setup, success or not (a restart of the router clears it too). Offline mode needs `MemAvailable` of at least 24000 KB plus the bundle's size; otherwise the fallback.
A7. **The flow on a factory router:** the setup program reads the router and builds the whole bundle on the computer first (nothing on the router changes yet). At the factory address it pushes only `install.sh` and runs it with `--yes` (it moves the router to 10.0.0.1, as today; nothing is downloaded by the router). At 10.0.0.1 it pushes the bundle, then runs the setup command with `PISO_LOCAL_PKGS` exported next to the answers and `install.sh --local /tmp/piso-offline`. On a router already at 10.0.0.1 the first step is skipped.
A8. **"The router has internet"** (for the fallback) means the router answers the setup program's `ping -c 1 -W 3 1.1.1.1 || ping -c 1 -W 3 8.8.8.8` over SSH, the same test as `20-preflight.sh:38`.

## Decisions, part B (approved by the owner, 2026-10-23)
B1. **A command for older routers:** `piso-setup box-wifi-name` gives the box network the router's own name `PisoCoinBox-<id>` (and a new own password), by telling the box first and then switching the router, the way `rotate_box_wifi` already does. The rental phones' network keeps its name (phones are not touched).
B2. **Never by itself:** an update does not run it; the owner runs it (it takes the box off its network for up to four minutes).
B3. **Tell the owner:** `piso-setup status`, the setup summary and the setup program's Check-up say when the box network is still called `PisoCoinBox`, with the one command that fixes it.
B4. **Pairing says what to do:** the pairing tips and its failure message mention that another PisoHub router nearby may answer the setup name, and to switch that router off for a few minutes (or run the command on it).
B5. **If anything fails, the box keeps working:** before the switch, nothing changes; after the switch, the router keeps the new name and tells the owner to power-cycle the box (same as `rotate_box_wifi` today).

## Invariants touched
- **Money and time.** Part A: not touched (no change to the program, the payment queue or the data folder). Part B: no change to payments, the queue, the ledger or credit; during the switch the box is off its network for up to 240 s, and coins are kept in the box's queue and credited once afterwards (fact B9). The command says so and asks before it starts.
- **Only owner-signed software:** not weakened. Our installer is checked against its published sha256 exactly as `install.sh` does today (the owner's signature applies to updates, as today). OpenWrt packages are checked against OpenWrt's own signed indexes by the router before install, which today's online path also does through `opkg update`. Part B does not touch updates or signing (the box is told its new name over the existing admin request).

## Constraints
- Setup program: Python standard library only, one file. Router side: POSIX shell and what OpenWrt has (`usign`, `sha256sum`, `opkg`).
- The online path (today's) stays exactly as it is and keeps passing its tests.
- `install.sh --local` and `PISO_LOCAL_PKGS` are only used on a first setup; the hourly update and `piso-setup update` never use them.
- Firmware is not changed: the box already accepts `wifi_ssid` and `wifi_pass` in one `/save` (fact B4). Because it validates neither, `own_box_wifi_name` must check the name it sends (`PisoCoinBox-<id>` from `router_id`) before sending it; a name the box cannot use would leave the box unable to rejoin.
- The rental phones' network, its name and password are not changed.
- A router set up on 1.5.0 or later with its own name is not changed by part B (the command says "already has its own name" and stops).
- Generated files (`website/install.sh`, `setup/piso-setup*.sh`, `website/pisophone_setup.py`) are regenerated by `tools/build_piso_setup.py`. `setup/RELEASE` is raised once, to 1.5.18, for both parts together.

### Part A: the first setup without the router's internet
7. **Reading the router** [`test_offline_setup.py`]. `read_router_feeds` reads `/etc/openwrt_release`, `/etc/opkg/distfeeds.conf`, `opkg list-installed`, `/etc/opkg.conf` (`check_signature`), the presence of `usign` and `/etc/opkg/keys/*`, and `MemAvailable`, in one SSH command. An apk router (no `/etc/opkg/distfeeds.conf`, `apk` present), no `check_signature`, no `usign` or no keys each give "offline setup not possible: <reason>".
8. **Resolving packages** [`test_offline_setup.py`, fixture indexes]. `resolve_packages` returns the missing packages of fact A1 and their dependencies in install order: alternatives (`a | b`) take the one already installed, else the first; `Provides` satisfy a dependency (for example `libcurl`'s SSL library); already-installed packages are skipped; `libmicrohttpd-no-ssl` only when no `libmicrohttpd*` is installed; a dependency on a `kernel` version different from the router's, or a package not in any source, gives "offline setup not possible: <package> <reason>". Fixtures: a 23.05-like ramips/mt7621 set and a 24.10-like set, each with curl's SSL alternatives.
9. **Building the bundle** [`test_offline_setup.py`, local HTTP server]. `build_offline_bundle` downloads from the router's own source URLs (`http` and `https`) each needed `.ipk`, checks its size and sha256 against `Packages` on the computer too, saves each used source's `Packages` (unpacked from `Packages.gz` when only that is served) and `Packages.sig`, and the installer for the router's CPU (the same file choice as `install.sh`) with its `.sha256`, and `install.sh`. A download that fails or does not match: "offline setup not possible: <file> <reason>".
10. **Pushing the bundle** [`test_offline_setup.py`, stub SSH]. `push_offline_bundle` writes each file into `/tmp/piso-offline/` with one SSH command per file (`cat > <file>.part && mv <file>.part <file>`, the file's bytes on standard input; no `scp`, no `tar`), checks all sha256 on the router with `sha256sum` in one more command, and is skipped when the same bundle is already there (the second run at 10.0.0.1 after the address move). If `MemAvailable` is under 24000 KB plus the bundle's size: the fallback (decision A2).
11. **The router checks before it installs** [`router/tests/test_setup.py`, stub `usign`, `sha256sum`, `opkg`]. `install_local_packages`: every `Packages` must pass `usign -V` with `/etc/opkg/keys`; every `.ipk` in `order.txt` must be listed in one of them with the same sha256 and size; then one `opkg install` command with all the files, in `order.txt` order (opkg sees every new package at once, so their dependencies on each other are met). A bad signature, an unknown file or a wrong sha256: nothing installed, the setup stops with the reason. Test with a tampered `.ipk` and with a tampered `Packages`.
12. **Installer without internet** [`router/tests/test_setup.py`, `test_install.py`]. With `PISO_LOCAL_PKGS` set, the setup does not ping and does not run `opkg update`, installs through `install_local_packages`, and runs to the end with no network (all `wget`/`curl`/`ping` stubs fail). `install.sh --local <dir>` uses the files there, checks the installer's sha256 as today, and never calls `fetch`. Without the option and the setting everything is exactly as today (the existing tests pass unchanged).
13. **The whole flow, both ways** [`router/tests/test_pisophone_setup.py`, `test_offline_setup.py`]. A factory router with no internet: the setup program builds and pushes the bundle, the address move and the setup run without the router going online, and `/tmp/piso-offline/` is gone afterwards. When the bundle cannot be prepared and the router has internet: today's path runs and the message names the reason. When neither works: it stops before changing the router, with both reasons. `--router-online` runs today's path. `phone` (PisoPhone only) does nothing with the router, as today. The order of decision A7 is tested with a fake router that records each SSH command: no `wget`, `curl` or `opkg update` is ever sent in offline mode.

(b) With router 1 on its own name and powered on next to it, a factory-reset box pairs with router 2 at the first try. 15. **Gates:** `bash scripts/check_security_rules.sh`; the router and setup Python tests (`CLAUDE.md` section 3) and `test_offline_setup.py`, listed in `quality.yml`; `python3 tools/build_piso_setup.py --check`; ShellCheck on the changed shell files.

## Out of scope
- Part A: the one-line installer typed on the router (decision A1); apk-based OpenWrt (25.x and snapshots that use apk) — the fallback is used; installing `kmod-nft-bridge` or any kernel module the setup does not install today; updates (they keep using the router's internet and the owner's signature); a copy of the OpenWrt package sources kept on the website.
- Part B: changing the firmware's built-in setup name (it would break pairing for every box already sold); renaming the rental phones' network on older routers (phones would need to be set up again); detecting another router's hidden network by scanning (a hidden network's name is not visible in a scan).
- The computer-side address clash of fact B10 (see "Questions for later").
